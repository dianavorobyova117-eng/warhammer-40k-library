# 军表构建与审计规范（铁律）

> 本规范来自2026-09-03/04用户多轮纠错（±250误差、错砍真表、App阅读法误读），每条都有血泪史。违反任何一条=返工。

## 铁律（无例外）

1. **2000分硬上限**：军表只有2000分上限，没有"带"、没有±容差。引擎实算分>2000的表在App里交不进去=废表。
2. **不空分（2026-09-04用户定调v2）**：目标是**尽可能贴近2000**——凡是塞个强化、买个武器、加个便宜单位这种"不用抉择就能补"的分，必须补满，不许因为过了某条线就停手。**1960只是难以抉择时的放开线**（真的没有合理填充手段时才允许，且必须注明缺口原因）。交付时<2000必须附缺口说明（差多少/为什么/补齐路径）。
3. **用户真表神圣**：用户的四张真表（影剑BESTP1W9/风暴剑KKXRF41O/双超重IOHYPMUU/毒刃E0NDBR99）构成永不动，只许按用户提供的截图/原文修DB价格。
4. **单一口径**：声明pts=引擎构建后逐单位实算之和。禁止"声明一个数、引擎算另一个数"。

## App军表阅读法（导出格式=一支部队两套视图）

黑图书馆App导出的军表有两套段落，是**同一批部队的两种视图**：

| 段落 | 性质 |
|---|---|
| 联合单位 | 组合视图：领导+护卫绑在一起展示，**本身不计分** |
| 人物 / 战线 / 专属运输载具 / 其他单位 | 分类视图：**计分段**。领导分记人物段，护卫分记其真实分类段 |

判定法则：
- 分类段条目若在联合段出现过（同分同名）→ **同一单位，绝不重复计**。文本导出中该条目会带"删除某领导"标注（截图上是删除按钮）
- 分类段中出现但联合段没有的 → 真实独立部队
- **数部队数 = 联合段联合数 + 分类段中非联合护卫的独立条目**
- App标题分（如"2000/2000满分"）= 上限判定显示，不是逐单位加总。逐单位加总可能>标题分（强化费/武器升级费口径），以逐单位加总为真实战力
- App标注的单位分 = 基础价 + 武器升级费 + 强化费（如"暴风兵指挥组100分"=85基础+夸大级15）

## 强化费与武器升级

- DB（units_all.json）存**基础价/常见配置价**
- 表内单位带强化/武器升级时，差额用 `|enhNN` 标签追加：`毒刃|enh30`（营部指挥官30分）
- 已知强化价：大战略家15 / 夸大级通讯阵列15 / 精英教头20 / 营部指挥官30 / 泰坦杀手20 / 侦察之星勋章10 / 机械对话者15 / 钻训指挥官20 / 临危不乱15 / 远距离斥候10
- 武器升级费（激光炮5分/多管热熔5分等）同样用enh标签：`黎曼鲁斯战斗坦克|enh15`（=激光炮5+双多管热熔10）
- **自查自创表时必查**：App原表的领导几乎都带强化，自创表一个强化没有=明显偷分

## 构建流程（每次新建/修改表）

1. 定核心思想（团策+流派），选主力单位
2. 逐单位从 data/units_all.json 取价（缺档单位**禁用**——静默跳过=分值缩水）
3. 补强化/武器升级enh标签（对照同类App表：领导带强化是常态）
   - **强化分配三步(2026-09-04泰坦杀手事故, 违反=返工)**: ①先读该强化的**适用限制原文**(如TITANIC CHARACTER only/ENGINSEER only), 名字和价格对≠能带 ②挂**最受益单位**(主输出/大枪/能力互补——泰坦杀手给风暴之剑不给指挥官) ③每军每件一次, 全部分配完再看缺口
   - 价格已核但限制未读=没核(括号摘要≠原文的强化版)
4. 逼近2000：能塞便宜占位（屁精/信徒/哨兵/小型载具）就塞，**不许空着**；留缺口必须说明原因
5. 验证四连：
   ```bash
   cd 模拟器 && python3 -c "
   import sys; sys.path.insert(0,'engine')
   from ref import Battle, LISTS
   l=next(x for x in LISTS['<族>'] if x['name']=='<表名>')
   b=Battle(l, LISTS['orc'][0], seed=1)
   print('引擎分:', sum(p.pts for p in b.ig), '| 单位数:', len(b.ig), '| 声明:', l['pts'])"
   ```
   - 引擎分 ≤ 2000 且 ≥ 1950（理想=2000）
   - 单位数 == units数组条目数（有跳过=缺档）
6. 提交前全库铁律扫描：所有表引擎分≤2000

## 审计流程（审计别人的表/全库自查）

- 重复计分检查：attach护卫与独立同名条目并存 → 对照App原文判断是"真第二队"还是"重复展示"
- 双领导联合（里昂+卡指挥组）合法，但矩阵校验只管领导×护卫
- 声明分差>30逐单位定责，不许"整体在带内"糊弄
- 每张表进引擎实测，不许只看声明字段
